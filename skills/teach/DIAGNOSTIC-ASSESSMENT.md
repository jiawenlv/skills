# Diagnostic assessment

Use assessment to choose the next teaching step for this mission. It is a provisional sample of abilities, not a certification or a universal level score.

## Scope and consent

Read the mission, active learning records, prior assessment evidence, and notes first. If the learner already requested testing, begin within that scope. Otherwise offer a brief diagnostic, usually 5–10 minutes, with an option to skip. A decline must not block teaching. Narrow a repeat diagnostic to the actual uncertainty.

Select a few mission-relevant capabilities and define observable success criteria before authoring questions. Verify expected answers against trusted resources. For example, an API integration mission may need data modelling and runtime validation before advanced type puzzles.

## Questions and adaptation

Start near the learner's reported experience; with no evidence, start with an accessible probe. Prefer predicting, explaining, fixing, or producing something over recalling names. Ask for reasoning or a small application to distinguish understanding from a lucky choice. Provide an explicit 'I do not know yet' or skip path. Avoid answer clues from option length or formatting; keep choice wording parallel.

After an unaided attempt, offer feedback. Record the first response separately from retries or hints. Strong reasoning can justify a harder or transfer task; a misconception should lead to a simpler prerequisite probe. Stop when there is enough evidence to choose a first lesson, when the agreed time is reached, or when the learner wants to stop. Do not require a fixed question count or a complete topic survey.

For programming, distinguish compilation, runtime behavior, and explanation. Executable checks should match the actual learning objective, use known tooling/version, and accept valid alternative solutions. If code was not executed, label the judgement as review, not a passing test. For drawing or handwriting, use a small work sample and observable criteria; request the sample if it is needed and unavailable rather than inferring ability from quiz answers.

## Artifact and feedback handoff

Conduct the diagnostic in chat, one small prompt at a time. If retaining the questions helps future interpretation, save an optional numbered Markdown lesson using CONTENT-CONTRACT.md. Keep reference answers separate and provide explanations after the learner attempts the question.

Record first attempts separately from hints and retries. Until real answers arrive, put the current pending prompt in NOTES.md and hand control to the learner. No webpage, answer-export widget, API, or automatic collection is involved.

## Interpretation and durable evidence

Report per-capability findings such as demonstrated independently, demonstrated with help, needs practice, or not assessed. Explain the evidence and uncertainty. A single successful item is provisional; do not extrapolate to an entire field or long-term retention. Keep self-rated confidence separate from observed performance.

When diagnostic evidence changes the next teaching decision, save a concise finding under [CONTENT-CONTRACT.md](CONTENT-CONTRACT.md); related answers can support one record rather than a record per question. Include a task link, assistance, or response detail only as needed to interpret the finding. If the learner skips, retain disclosed knowledge or uncertainty only when useful for continuation. Never record an unattempted diagnostic as completed or mastered.

Recommend the next small skill and explain why the evidence supports it. Later, use a different task after a gap to assess retention or transfer. Keep old evidence when revising an assessment and link the superseding record. Do not create scheduled follow-ups without a user request.
